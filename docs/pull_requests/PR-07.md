## PR-07: Authorization and Business Data Isolation

### Objective
Enforce strict multi-tenant authorization boundaries ensuring every business account can access, modify, export, and delete only its own records. Reject any attempt to supply unauthorized `userId` attributes via request bodies, and guarantee that ownership is derived solely from verified authentication context.

### Existing problem
- The application previously accepted arbitrary client inputs without strict schema filtering, creating potential vectors for ID manipulation and mass assignment.
- While endpoints filtered by `userId`, there was no formal verification or automated testing proving that User A could not access, modify, export, or delete User B's receipts or flavours.
- Direct object reference vulnerabilities (IDOR) could allow cross-tenant data leakage if endpoints ever failed to bind `req.userId`.

### Implementation
1. **Strict Payload Filtering:**
   - Enforced `.strict()` on `createReceiptSchema`, `updateReceiptSchema`, `createFlavourSchema`, and `updateFlavourSchema`. Any attempt to send `userId`, `_id`, or unexpected fields is immediately rejected with HTTP 400.
2. **Deterministic Ownership Derivation:**
   - Confirmed that `receiptService` and `flavourService` derive document ownership exclusively from the verified JWT `req.userId` context.
   - All update, delete, and read operations query using compound predicates `{ _id: resourceId, userId: req.userId }`.
3. **Automated Cross-Tenant Isolation Tests (`backend/tests/dataIsolation.test.js`):**
   - Verified that forging `userId: userA` in flavour or receipt payloads is rejected with HTTP 400.
   - Verified that User B attempting to read User A's receipt by ID raises `NotFoundError` (preventing ID enumeration).
   - Verified that User B attempting to update or delete User A's receipt raises `NotFoundError`.
   - Verified that User B attempting to update or delete User A's flavours raises `NotFoundError`.
